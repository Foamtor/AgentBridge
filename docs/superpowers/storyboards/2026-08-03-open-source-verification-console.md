# AgentBridge 开源验证体验用户故事板

> **状态：** 已确认；2026-08-03 增补管理员首登故事  
> **日期：** 2026-08-03  
> **当前阶段：** 用户故事板；不作为功能规格或实施计划  
> **目标用户：** 刚 clone 仓库、想验证 AgentBridge 的开源开发者  
> **产品气质：** 克制、可信的开发者工具

## 1. 故事目标

用户第一次打开 AgentBridge 调试台时，不应先理解 thread ID、Bearer Token、SSE 事件或路由配置。首轮体验要先回答四个问题：

1. 项目是否已经正确启动，我能否安全地取得管理员访问权？
2. 它能否把现有业务数据变成可用的 Agent 结果？
3. 权限、审批、审计和幂等是否真的由平台处理？
4. 验证完成后，我该如何接入自己的业务？

核心故事是：开发者运行默认 Compose，从 API 容器日志取得只显示一次的管理员初始凭据，首次登录后强制设置自己的强密码；随后在完成改密后的三分钟内完成一次只读业务验证，再完成一次需要人工审批的写操作，按需检查平台证据，并能明确找到二次开发入口。

## 2. 用户与情境

### 主要用户

一位具备 Docker 和基本 Web/API 经验的开发者。他刚从 GitHub clone AgentBridge，可能尚未阅读完整架构文档，也没有准备模型 API Key、外部数据库或身份提供方。

### 使用情境

- 用户按照 README 执行 `docker compose up --build`。
- 默认 Compose 启用本地控制台管理员认证；用户尚未设置自己的密码。
- 默认环境使用 `dev` 租户、脱敏模拟工单、离线模型桩和 fake knowledge。
- 用户通过 `http://localhost:8080` 打开调试台。
- 用户的目标是判断这个仓库是否值得继续研究或用于自己的业务，而不是管理生产环境。

### 用户的初始疑虑

- 这是不是只能聊天的演示壳？
- 演示是否依赖未说明的云服务或 API Key？
- 默认管理员密码是不是所有安装都一样，是否会泄露或长期有效？
- 表格、图表和引用是业务结构化结果，还是前端写死的？
- “人工审批”是否真的阻止了批准前写入？
- 重复批准、断线或重试会不会重复创建业务记录？
- 我要接自己的 API 或数据库时，需要改核心代码吗？

## 3. 故事主线

```text
启动仓库
  -> 从 API 日志取得一次性管理员凭据
  -> 首次登录并强制设置强密码
  -> 确认环境就绪
  -> 一键运行只读场景
  -> 查看业务结果
  -> 按需检查平台证据
  -> 生成写操作草稿
  -> 人工批准并确认幂等结果
  -> 前往 SKILL.md 开始接入自己的业务
```

业务结果与技术证据贯穿同一次运行，但在界面叙事上分开：首屏优先展示“发生了什么”，技术证据用于回答“为什么可以相信”。

## 4. 分镜故事板

### 分镜 1：从 README 启动默认环境

**用户目标 / 问题**  
我能否不申请 API Key、不配置外部服务，直接把项目跑起来？

**屏幕 / 状态**  
终端显示 Compose 正在启动 Web、API 和 PostgreSQL。README 明确给出访问地址和默认环境边界。

**用户操作**  
执行 `docker compose up --build`，等待服务就绪，然后打开 `http://localhost:8080`。

**系统行为**  
初始化 `dev` 租户和脱敏工单数据；使用离线模型桩与 fake knowledge；若尚无本地管理员，创建 `admin` 账号和随机一次性初始密码，仅向 API 容器日志输出一次；Web 通过同源 `/api` 访问 API。

**可信证据**  
启动命令、容器健康状态和访问地址一致；仓库和镜像中没有固定默认密码；所有演示依赖均在仓库与 Compose 中可追溯。

**失败与恢复**  
若服务未就绪，登录页显示 API 不可用并指向对应日志命令。若初始密码日志遗失，管理员通过容器内恢复命令轮换一次性密码；系统不得重新显示旧密码。

**产品信息**  
AgentBridge 的首次验证可以完全在本机完成。

### 分镜 2：管理员首次登录并设置强密码

**用户目标 / 问题**  
我如何安全进入控制台，并确保安装后不继续使用临时凭据？

**屏幕 / 状态**  
浏览器首先显示简洁的管理员登录页。用户使用固定用户名 `admin` 和 API 日志中的一次性初始密码登录后，只能进入“设置新密码”页，不能访问验证、契约或管理功能。

**用户操作**  
输入一次性凭据；随后输入并确认自己的新密码，满足页面实时显示的强度要求。

**系统行为**  
服务端验证初始密码哈希及一次性状态，签发受限的改密会话。新密码通过服务端策略后以 Argon2id 哈希保存，使初始凭据立即失效，撤销旧会话，并签发正常管理员会话。

**可信证据**  
页面明确说明初始密码只显示一次且改密后失效；密码策略同时说明最小长度、常见口令拦截和长口令支持；浏览器不接触或保存可复用 Bearer Token。

**失败与恢复**  
登录失败不泄露账号是否存在；连续失败触发渐进等待。初始化凭据过期或遗失时，页面只给出本机恢复命令，不提供安全问题或邮件找回。改密失败时受限会话仍不能访问其他页面。

**产品信息**  
默认开源体验有真实的管理员边界，但不要求用户先部署外部身份系统。

### 分镜 3：打开验证工作台

**用户目标 / 问题**  
项目是否正确启动？我现在应该做什么？

**屏幕 / 状态**  
首屏是验证工作台，而不是后台概览或空白聊天框。页面清楚显示 API、数据库和演示数据已就绪，并标注“技术预览”“脱敏模拟数据”“离线运行”。默认业务参考为 `work_order_ops`。

**用户操作**  
查看环境摘要，选择首个推荐场景“查询并分析工单”。

**系统行为**  
预先准备正确的 route、租户和演示权限；线程、Token、冲突测试等参数使用安全默认值并留在高级设置中。

**可信证据**  
页面区分已连接、检查中、不可用三种状态；展示当前运行模式与数据性质，不把模拟能力伪装成生产服务。

**失败与恢复**  
若 API 或数据库不可用，推荐场景不可执行，页面保留诊断信息和重试检查；已经就绪的组件仍独立显示状态。

**产品信息**  
这是用于验证平台能力的开发者工作台，不是最终业务前端。

### 分镜 4：一键运行只读黄金场景

**用户目标 / 问题**  
AgentBridge 能否从业务数据产生真实、结构化的结果，而不只是返回一段文本？

**屏幕 / 状态**  
推荐场景展示预期范围：读取脱敏工单、生成列表与状态分布图，不执行写操作。运行期间显示清晰的进行中状态和当前步骤。

**用户操作**  
点击一次“运行场景”。无需先选择预设、再点击发送。

**系统行为**  
向 `work_order_ops` 发起标准流式请求，查询当前租户的工单，依次产生文本、列表和图表业务事件，并在同一次运行中结束。

**可信证据**  
运行状态从等待、运行中到成功有明确变化；结果标注来源为 `work_order_ops`，并显示只读权限范围和耗时摘要。

**失败与恢复**  
用户可取消正在运行的请求。失败时保留已收到的结果，指出失败阶段，并提供“重新运行”；不把部分结果误报为完整成功。

**产品信息**  
业务插件负责业务能力，平台负责一次运行的生命周期与有序输出。

---

### 分镜 5：先理解业务结果，再查看实现证据

**用户目标 / 问题**  
这次运行到底产出了什么？结果是否可供业务界面直接渲染？

**屏幕 / 状态**  
主要结果区展示工单表格、统计图表和简短结论。字段为脱敏业务字段；空数据、截断和图表降级均有明确语义。协议事件不穿插在业务内容中。

**用户操作**  
浏览表格和图表；需要进一步验证时，打开与本次运行关联的“技术证据”。

**系统行为**  
前端按结构化扩展事件渲染结果；图表不可用时退化为可读的数据列表，不丢失业务信息。

**可信证据**  
技术证据显示本次运行可见的工具、实际工具调用、有序事件、route、租户与权限决策摘要；原始 JSON 可继续展开，但不是默认内容。

**失败与恢复**  
若某种结果无法渲染，页面保留其结构化数据与原始事件入口，并明确说明渲染失败，不将其等同于后端失败。

**产品信息**  
AgentBridge 输出的不只是聊天文本，而是业务前端可消费的结构化结果；平台证据与业务结果可以独立检查。

### 分镜 6：生成审批前的写操作草稿

**用户目标 / 问题**  
涉及写入时，Agent 会不会未经确认就修改业务数据？

**屏幕 / 状态**  
第二个推荐场景“创建工单并写入台账”明确标注“需要人工审批”。运行结果先展示不可变的工单草稿和台账预览，包括标题、优先级、处理人和摘要。

**用户操作**  
运行写操作场景，检查草稿内容。

**系统行为**  
平台在批准前只持久化审批记录与 action envelope，不创建工单或台账；运行进入“等待人工决定”状态。

**可信证据**  
页面明确显示“尚未写入”，列出将执行的动作、审批有效期和必要权限；草稿与待批准动作内容一致。

**失败与恢复**  
草稿校验失败、处理人不可用或权限不足时，不进入可批准状态；页面说明拒绝原因且保持零写入。用户可调整输入后重新生成草稿。

**产品信息**  
模型提出动作，平台冻结待执行内容，人决定是否真正写入。

---

### 分镜 7：批准、拒绝与等待状态

**用户目标 / 问题**  
审批是不是一个真实的流程状态，而不是装饰按钮？

**屏幕 / 状态**  
审批区域将“批准”和“拒绝”作为清晰的业务决策，并持续显示等待中、提交中、执行中、成功、拒绝、过期或失败状态。危险操作不会因重复点击产生多次提交。

**用户操作**  
本次选择“批准”；也可以在另一轮选择“拒绝”验证零写入。

**系统行为**  
批准时重新校验请求人与审批人的权限，原子 claim 执行权，在单一事务中创建工单与台账；拒绝或超时则终止且零写入。

**可信证据**  
技术证据显示审批状态迁移、二次鉴权和执行结果；界面不要求首次用户理解内部审批 ID，但允许在详情中复制。

**失败与恢复**  
网络中断或执行状态暂不确定时，页面查询审批记录恢复真实状态，不鼓励用户盲目重复执行。可重试失败与已提交但结果事件未送达必须被区分。

**产品信息**  
人工审批是平台控制的执行边界，不是模型的一句自然语言承诺。

---

### 分镜 8：确认写入结果与幂等性

**用户目标 / 问题**  
工单和台账是否都创建成功？重复批准会不会生成重复记录？

**屏幕 / 状态**  
成功结果以可读摘要呈现新工单号、台账号、处理人和状态，并明确“工单与台账已在同一事务中创建”。本次审批被标记为已完成。

**用户操作**  
查看创建结果；在技术验证入口执行一次受控的“检查幂等结果”，而不是把冲突测试作为首屏主操作。

**系统行为**  
相同审批再次查询或恢复时返回同一结果，不新增工单或台账；结果可通过审批记录重建。

**可信证据**  
前后两次结果使用同一工单号和台账号；审计摘要显示一次业务提交。原始事件与审批 ID 可在详情中关联。

**失败与恢复**  
若业务事务失败，工单和台账均不应部分存在；页面显示执行失败而非创建成功。若业务已提交但结果事件送达失败，页面恢复持久化成功结果并说明事件异常。

**产品信息**  
平台让审批后的写操作可追溯、可恢复且不会因重试重复执行。

---

### 分镜 9：从验证转向自己的业务

**用户目标 / 问题**  
我已经确认平台能工作，下一步怎样接入自己的 API 或数据库？

**屏幕 / 状态**  
验证完成摘要列出已证明的能力：结构化查询、图表、知识引用、审批写入、幂等执行和技术证据。页面提供清晰的“接入自己的业务”下一步，而不是继续堆叠演示操作。

**用户操作**  
打开 `SKILL.md` 或 `docs/ai-instructions/05-ai-coding.md`，复制面向 AI 编程助手的起始提示词；按需查看 `work_order_ops` 源码与高级调试功能。

**系统行为**  
将用户引导到插件开发路径：描述现有接口，基于 `_scaffold` 编写自己的 `domain/tools/tests`，再用同一工作台验证。

**可信证据**  
下一步同时链接插件模板、参考实现、架构 MUST 和测试命令；明确 `work_order_ops` 是参考业务，不是 core 内置行业系统。

**失败与恢复**  
文档链接不可用时仍显示准确的仓库相对路径和可复制命令；离开页面不会清除刚完成的运行证据。

**产品信息**  
AgentBridge 是源码型业务 AI 底座：验证参考实现之后，真正的交付是让开发者写自己的业务插件。

## 5. 横向状态故事

以下状态必须在后续功能设计中统一定义，避免每个区域自行发明文案和颜色：

| 状态 | 用户需要知道什么 | 必须提供的动作 |
|------|------------------|----------------|
| 检查中 | 系统正在确认哪些组件 | 等待；必要时查看诊断 |
| 未登录 | 需要管理员身份才能进入控制台 | 登录 |
| 必须改密 | 初始凭据有效，但还不能使用控制台 | 设置强密码 |
| 就绪 | 哪些能力可直接验证 | 运行推荐场景 |
| 运行中 | 当前执行到哪一步，是否仍有响应 | 取消；查看实时证据 |
| 等待审批 | 尚未写入，等待谁做什么决定 | 批准或拒绝 |
| 成功 | 产生了哪些业务结果 | 查看结果与证据；进入下一场景 |
| 已拒绝 / 已取消 | 操作已终止且是否零写入 | 重新运行 |
| 可恢复失败 | 真实状态可查询，是否允许安全重试 | 恢复状态；安全重试 |
| 终端失败 | 失败阶段、影响范围和诊断入口 | 查看诊断；重新运行 |

## 6. 语言与信任原则

- 全局使用中文或英文一种语言完成主要流程，不出现中英文混排的主导航和核心操作。
- 业务术语可以本地化；route、事件类型、权限名等代码标识仅在技术证据中保留原文。
- 始终明确演示数据为脱敏模拟数据、默认模型为离线桩、当前版本为技术预览。
- 不用“智能”“强大”等口号代替可验证事实；每项能力都应能关联到一次运行结果或技术证据。
- 高级参数按需展开，不让 Token、thread ID、原始 SSE 或 409 测试成为首次使用门槛。
- 管理后台属于次级入口；默认首页服务于开源开发者的首次验证任务。

## 7. 首轮体验成功判据

故事完成时，首次用户应能够：

1. 从日志取得每个安装唯一的一次性管理员密码，并在首次登录后完成强制改密。
2. 未登录或未完成改密时无法访问控制台能力。
3. 不配置 API Key，在页面确认默认环境是否就绪。
4. 通过一次操作运行只读黄金场景，并看到表格和图表。
5. 区分业务结果、平台运行状态与原始协议证据。
6. 在审批前确认尚未写入，并能审阅冻结的草稿。
7. 批准后看到工单与台账的可读创建结果。
8. 理解相同审批重试不会重复创建记录。
9. 随时识别当前是等待、运行、成功、失败、取消还是审批状态。
10. 使用统一的中文或英文完成整个主要流程。
11. 明确演示环境的模拟数据、离线能力与技术预览边界。
12. 找到 `SKILL.md`、插件模板、参考 domain 和验证命令，开始自己的业务接入。

## 8. 留给下一阶段的问题

以下内容不在故事板阶段拍板，将在“功能设计”中定义：

- 登录、强制改密与工作台的具体信息架构、导航层级和页面路由。
- 三个推荐场景的最终划分、命名和默认输入。
- 业务结果与技术证据采用分栏、标签页还是可展开区域。
- 环境就绪检查所需的 API 聚合方式与刷新策略。
- 审批恢复、幂等检查和审计摘要的具体交互。
- 中英文资源组织方式、默认语言与持久化策略。
- 桌面窗口宽度边界、键盘操作和无障碍细节；首版不设计移动布局。
- 与现有管理页面的保留、降级或重新归类方案。

## 9. 阶段门

只有在本故事板确认后，才进入功能设计。功能设计需要把上述九个分镜映射为页面、状态、数据契约和操作，但不得改变以下主线：

> 先安全取得管理员访问权并完成强制改密，再确认环境和验证业务价值；先看业务结果，再按需检查平台证据；写操作先冻结草稿，经人工批准后才执行；验证完成后引导开发者编写自己的插件。
