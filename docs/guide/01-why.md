# 为什么用 AgentBridge

---

## 先用一句话说清楚

要把**已有业务系统**接到 **AI 对话**上时，别每次从「流式输出、登录、权限、会话别抢跑」重写一遍。

AgentBridge 是一层**自托管的公共底座**（软件装在你自己的机器/机房上）：  
公共能力平台统一做；你的业务做成**插件**插上去。

## 一个具体画面

用户在聊天框问：「这张申请单到哪一步了？」

1. 你们的前端（或本仓库调试页）把问题发给 AgentBridge API  
2. 请求里写明用哪个业务插件（`route`）  
3. 插件去调你们的查单工具、拼回答  
4. 平台负责一边生成一边往客户端推消息，并管好会话、权限、审计这类公共事  

客户看到的「一张图 / 政务工作台」前端**不在本仓库做**；本仓库提供 API + 一个给集成同学用的调试页。

## 常见痛点 → 底座怎么帮

| 痛点 | 底座怎么帮 |
|------|------------|
| 流式、取消、同一会话别两个人抢着跑，每次重写 | 平台统一做 |
| 业务代码和框架搅在一起 | 业务进 `apps/api/domains/`，核心库不写死业务名 |
| 权限、审计各搞一套 | 统一约定，可按需打开 |

## 仓库里三块东西（别混）

| 块 | 是什么 | 在哪 |
|----|--------|------|
| **底座** | 对话 API、工具与数据/知识的「插座」 | 核心库 `packages/core` + 服务壳 `apps/api`（不含业务文件夹时，也可笼统叫平台） |
| **业务插件** | 某个场景怎么聊、调哪些工具 | **挂在** `apps/api/domains/`（如 `echo`、`demo_rag`）——和平台代码同仓，但是你自己的业务 |
| **AI 控制台** | 给集成方/管理员调试和查看 | `apps/web` |

注意：`apps/api` 里既有平台服务，也有 `domains/`。不要把「整个 `apps/api`」都当成你的业务代码。

## 做 / 不做

**做：** 自己服务器上的 Agent API；多个业务插件共用一套接口；权限、查库、知识库、审批等按需打开。

**不做：**

- 替代 LangGraph 官方云产品（你不是来「租他们的云工作室」的）  
- 当企业账号中心（谁登录、组织架构）——可对接你们现有登录（如 OIDC），但不取代整套账号体系（常叫 IAM）  
- 默认「多台机器随便扩」——多机要按文档显式配置
