# 发布规划：v1.0.0 单机稳定版

> **状态：** v1.0.0 单机发布门槛已完成并以 tag 发布（`a6e07ba`）；后续文档口径修订见 `main` 的 `49a4566`。
>
> **目标：** 发布可信、易读、可二次开发的源码型底座，以传统业务查询、图表、台账与审批黄金案例证明价值。
>
> **边界：** 平台负责对话运行、JSON/SSE、权限、审批、审计与 RAG Port；业务系统和 AI 负责 domain/tools 与最终业务页面。

## 1. 发布定位

**一句话：** AgentBridge 帮传统业务系统以受控、可审计的方式接入 AI：既能检索知识，也能按权限调用业务工具。

首个发布不是通用 AI Studio，也不只是 RAG 演示。它必须能展示以下闭环：

```text
业务用户 / 业务前端
        │
        ▼
AgentBridge：身份、权限、会话、流式、审计、回放
        ├── 业务插件：查询工单 / 订单 / 设备等结构化数据
        ├── RAG：检索手册 / 规范 / FAQ，并返回引用
        └── 受控写工具：必须经过审批后才执行
```

## 2. 已有基础与发布缺口

| 范围 | 当前状态 | 1.0 状态 |
|------|----------|----------------|
| M0–M10 平台能力 | 已实现并有单元/集成测试与 CI 门禁 | ✅ 已完成 |
| M11 多知识后端 | `fake`、`langchain_pg`、`external` 与 `/ingest` 已实现 | ✅ 契约和边界已完成；厂商联调为后续项 |
| M12 开发者控制台 | 验证、插件调试、C0–C4 管理页面及相应 API 已实现 | ✅ Web 构建、权限和管理闭环已完成 |
| 传统业务改造 | `work_order_ops` 黄金参考实现已合入，并完成真实 PG/RAG 验收 | ✅ 1.0 黄金案例已完成 |
| 发布工程 | MIT、Python/API/SDK CI 已有 | ✅ 版本、变更记录、贡献与安全政策已发布 |

**状态定义：** “已实现”不等于“已发布”。下列阶段均以可重复的验收记录为完成条件。

## 3. 发布范围与非目标

### v1.0.0 发布范围

1. 中英文 README、AI 读仓路径与可复制 tools 开发提示词。
2. 一套默认零模型密钥的 Web/API/PostgreSQL Compose 体验。
3. `work_order_ops` 黄金案例：脱敏数据查询、图表、citation、台账草稿、审批与创建。
4. 已有 JSON/SSE、工具双鉴权、审计与审批能力的可见验证。
5. 贡献、安全、变更记录与真实限制说明。

### 明确不作为 v1.0.0 阻塞项

- 云托管 Studio 或客户业务前端成品；
- 文档解析/OCR/知识生产流水线全家桶；
- 任意多 Agent 群聊框架；
- 默认零配置的多机高可用；
- 1.0 之后的生产部署演练、升级回滚、备份恢复、具体 IdP 联调与多机验收；
- PyPI/npm/GHCR、SBOM、镜像签名等公共制品与供应链发布工程。

外部知识后端可以只支持检索；对于不支持摄取的后端，`POST /ingest` 返回 501 是约定的能力边界，必须在支持矩阵中说明。

## 4. 执行阶段

### P0：冻结发布基线与对外口径

**目的：** 让文档、代码、版本和支持边界说同一种语言。

- 统一路线图，补充 M11/M12 的实现状态和发布验收状态。
- 确定首个版本号与命名；`v1.0.0` 的单机发布口径由 M0–M4、黄金案例、P2-A 与 P3 门禁定义。
- 输出支持矩阵：Python、PostgreSQL/pgvector、Redis、OIDC、模型 Gateway、知识后端。
- 记录已知限制：单机/多机条件、外部 RAG ingest 限制、控制台热配置的生产边界。

**完成标准：** README、路线图、部署文档和 release notes 不再存在“已完成”“规划中”“生产可用”相互冲突的描述。`v1.0.0` 的发布门槛是 P0、P1、P2-A、P3、黄金案例、单机真实 Postgres/认证/模型出口、全套 CI 和公开漏洞报告渠道；P2-B 不属于 1.0.0 阻塞项。

### P1：黄金参考实现——售后工单助手

**目的：** 验证传统业务改造的接入成本和平台边界。

建议场景可替换为订单、设备运维等，但必须同时覆盖结构化业务数据和非结构化知识。

| 能力 | 参考实现行为 | 验收 |
|------|--------------|------|
| 业务查询 | 按租户和角色查询工单/订单状态 | 无权限工具不可见；越权执行仍被拒绝 |
| RAG | 检索产品手册、SOP、FAQ | 回答携带 citation；跨租户检索失败 |
| 写操作 | 例如升级工单或创建处理建议 | 进入审批；超时默认不执行；恢复使用同一 run |
| 运行保障 | SSE、取消、回放、审计 | 可按 run_id 复盘已提交事件与关键决策 |

**实现约束：** 仅在 `apps/api/domains/<reference_domain>/` 写业务；检索与数据源通过已注入 Port 使用，不在 domain 创建 adapter 或直接推 SSE。

**完成标准：** 新环境按文档可跑通上述场景；记录接入步骤、配置、接口权限和故障排查方法。

### P2：生产验证矩阵（P2-A 已完成）

**目的：** 将“代码实现”升级为“可验证的运行承诺”。

P2 分为两类：**P2-A** 是 1.0.0 必须完成的运行、安全、RAG 契约与控制台门禁；**P2-B** 是 1.0.0 之后的部署与扩展验证，不阻塞单机稳定版。

#### P2-A：v1.0.0 必验项

| 类别 | 已验收场景 |
|------|----------|
| 安全 | OIDC/JWT、跨租户、工具越权、审批超时、审计导出脱敏 |
| RAG | pgvector 摄取/检索、external 检索、后端不支持 ingest、检索超时降级、引用正确性 |
| 稳定性 | 断连/取消、EventLog 写入失败、限流、依赖不可用 |
| 控制台 | Web build、管理员/普通用户权限、调试→回放→审计闭环 |

**P2-A 状态：已完成（2026-08-01）。** 已验证认证与权限、跨租户、审批/审计、pgvector 与只读 RAG-Agent、external HTTP 契约、取消/EventLog、单机限流/readiness、Web build 与控制台权限。验收记录见 `docs/release-validation/`。

#### P2-B：1.0.0 后续验证项

| 类别 | 后续场景 |
|------|----------|
| 部署恢复 | 全新环境部署、数据库迁移、升级与回滚、备份恢复 |
| 身份联调 | 具体身份提供方现场登录 |
| 外部集成 | 厂商 external RAG 联调 |
| 多机 | 双实例 Redis 锁与跨实例限流 |

这些能力可以在 1.0.0 发布后逐项补充，不改变单机版本承诺。

**完成标准：** P2-A 须有自动化测试、脚本或人工验收记录并作为 1.0.0 门禁；P2-B 作为后续工程单独记录验证结果。失败项和环境前提进入已知限制，而不是从文档中消失。

### P3：发布工程与社区入口（已完成）

**目的：** 让外部使用者能安装、判断边界、报告问题并安全升级。

- 将 Web `build` 加入 CI；保留 Python、SDK、架构与 eval 门禁。
- 提供版本化发布说明、迁移/升级说明和可复现部署产物（至少容器化 API 或明确的构建流程）。
- 新增 `CONTRIBUTING.md`、`SECURITY.md`、`CHANGELOG.md`。
- 发布参考实现、示例数据与脱敏后的验收记录。

**完成标准：** 干净环境可依据公开文档安装、启动、验收参考实现；发布包、Git tag 和变更记录可追溯。

## 5. 优先级与决策规则

1. P0 与 P1 优先于任何新平台能力。
2. P2 发现的问题，优先修正已有抽象或文档，不以新增功能掩盖。
3. 只有黄金参考实现无法在 domain 层完成的共性能力，才进入 `packages/core`；仍须遵守 Port/Adapter 分层。
4. 多机仅在 P2 双实例验收通过后才作为首发承诺；否则清楚标为实验性或后续能力。
5. RAG 的成功指标是“受权限约束且可追溯的知识回答”，不是接入的向量库数量。

## 6. 发布门槛

满足以下条件即可标记为 `v1.0.0` 单机稳定版：

- P0、P1、P2-A、P3 完成；
- 黄金参考实现完成端到端验收；
- 默认生产路径使用真实 Postgres、认证和模型出口，而非 Fake/stub；
- 所有架构门禁、Python/API/SDK/Web CI 通过；
- RAG 支持矩阵和 external ingest 的限制对外明确；
- 已知风险、升级路径和漏洞报告渠道已公开。

P2-B 的部署恢复、具体 IdP 和多机验证不属于上述门槛；未完成时不得宣称默认多机可用，但不影响单机 `v1.0.0` 口径。
